# Self-hosted Supabase — vendored stack

This directory is the **entire backend** of ICC Desk: Postgres, Auth, REST,
Realtime and Storage behind a Kong gateway, running as Docker containers on the
project's own VPS instead of Supabase Cloud.

It is deployed to `/srv/supabase` on `72.62.42.52` and started by the
`supabase.service` systemd unit. The only public entrance is nginx on 443,
which proxies `https://chat.icenterconsult.com/sb/` to Kong on
`127.0.0.1:8001` (port 8000 belongs to an unrelated stack on the same box).

- Day-to-day operations: **[`docs/RUNBOOK.md`](../../docs/RUNBOOK.md)**
- Why it is built this way: **[the implementation plan](../../docs/superpowers/plans/2026-09-02-self-hosted-supabase.md)**

> **This repository is public.** Everything here is a template. No key,
> password or token may ever be committed. Real values live only in
> `/srv/supabase/.env` on the server — `chmod 600`, root-owned, generated by
> `generate-secrets.sh`. The `$SUPABASE_*` tokens in `volumes/api/kong.yml`
> are shell placeholders substituted at container start, not secrets.

## The six services we keep

| Service | Image (pinned) | Memory cap | Published port |
|---|---|---|---|
| `db` | `supabase/postgres:17.6.1.136` | 1500m | **none** |
| `auth` | `supabase/gotrue:v2.189.0` | 256m | none |
| `rest` | `postgrest/postgrest:v14.12` | 256m | none |
| `realtime` | `supabase/realtime:v2.102.3` | 512m | none |
| `storage` | `supabase/storage-api:v1.60.4` | 384m | none |
| `kong` | `kong/kong:3.9.1` | 512m | `127.0.0.1:8000` |

Postgres is 17 to match the cloud project, so dumps restore without a version
jump. Nothing listens on a public interface: Kong binds loopback and the
database port is not published at all — reach it with
`docker compose exec -T db psql -U supabase_admin -d postgres`.

## What was removed, and why

Upstream's `docker/docker-compose.yml` ships eleven services; two more
(`analytics`, `vector`) arrive via `docker-compose.logs.yml`. We run six.

| Removed | Reason |
|---|---|
| `analytics` (Logflare) | **The documented cause of OOM on a 2 GB box**, and of runaway WAL growth — it holds a replication-fed pipeline open against Postgres. Never enable it here. |
| `vector` | Only feeds `analytics`; also needs a bind mount of the Docker socket, which we will not grant. |
| `studio` | The dashboard. Publishing it means publishing a second credentialed web surface; the app's own Admin screens and `psql` cover what we need. |
| `meta` (`postgres-meta`) | Exists only to serve Studio. |
| `functions` (edge-runtime) | No Edge Functions in this project. Would idle a Deno runtime. |
| `imgproxy` | On-the-fly image transformation. The app never requests transformed URLs, so `ENABLE_IMAGE_TRANSFORMATION` is set to `"false"` on `storage`. |
| `supavisor` (pooler) | A connection pooler, and upstream's only reason to publish `5432` on the host. Next.js uses PostgREST over HTTP, not raw Postgres. |

`analytics` and `vector` are the two named in the plan's global constraints:
they are **never** to be enabled on this box.

## Delta from upstream

Beyond deleting the seven service blocks, the vendored `docker-compose.yml`
differs from upstream in exactly these ways. Nothing else was touched, so an
upgrade stays a readable diff.

1. **Rewritten `depends_on`.** A `depends_on` naming a pruned service blocks
   the whole stack from starting — this is the single most likely cause of a
   failed first boot.
   - `kong` waited on `studio: service_healthy`; it now waits on `auth`,
     `rest`, `realtime` and `storage` at `service_started`, so a slow backend
     cannot wedge the gateway.
   - `storage` waited on `db`, `rest` **and `imgproxy`**; the `imgproxy` entry
     is gone.
   - `auth`, `rest`, `realtime` and `db` are unchanged.
2. **Ports.** Kong is hardcoded to `127.0.0.1:8000:8000` (upstream:
   `${KONG_HTTP_PORT}:8000`). Kong's `8443` mapping is dropped — nginx
   terminates TLS. The `db` service publishes nothing, and `supavisor`, which
   was what published `${POSTGRES_PORT}` on the host, is gone.
3. **`restart: unless-stopped` and `mem_limit` on all six**, sized for a 2 GB
   box (table above).
4. **`db` command** gains `-c wal_level=logical -c max_slot_wal_keep_size=512MB`.
   The bound is the important half: a lagging replication slot gets dropped
   instead of pinning WAL until the disk fills.
5. **`storage`**: `ENABLE_IMAGE_TRANSFORMATION` forced to `"false"` and
   `IMGPROXY_URL` removed; `FILE_SIZE_LIMIT` and `STORAGE_BACKEND` moved into
   the environment file.
6. **`kong`**: `basic-auth` and `ip-restriction` dropped from `KONG_PLUGINS`
   along with the routes that used them; `DASHBOARD_USERNAME` /
   `DASHBOARD_PASSWORD` removed.
7. Commented-out upstream blocks for asymmetric JWKs, OAuth providers, SMS,
   MFA and SAML are dropped for readability. They are recoverable from the tag
   above.

### Support files

Only what the six services actually mount is vendored:

```
volumes/api/kong.yml             gateway routes (pruned, see its header)
volumes/api/kong-entrypoint.sh   env substitution into the declarative config
volumes/db/realtime.sql          creates the _realtime schema
volumes/db/roles.sql             sets passwords for authenticator / auth / storage roles
volumes/db/jwt.sql               seeds app.settings.jwt_secret and jwt_exp
volumes/db/webhooks.sql          pg_net + supabase_functions schema (DB webhooks;
                                 unrelated to the pruned edge-runtime service, and
                                 present in the cloud schema we restore)
```

Deliberately **not** vendored: `volumes/db/_supabase.sql`, `logs.sql` and
`pooler.sql` (they build the `_supabase` database and its `_analytics` /
`_supavisor` schemas, used only by Logflare and Supavisor), `volumes/logs/`,
`volumes/pooler/`, `volumes/functions/`, `volumes/snippets/`,
`volumes/api/envoy/` and `volumes/proxy/`.

`volumes/db/data` and `volumes/storage` are runtime data directories. They are
created on the server and are not in git.

## Environment

Copy `.env.example` to `/srv/supabase/.env` and fill it with
`generate-secrets.sh`. `ANON_KEY` and `SERVICE_ROLE_KEY` are **not random
strings** — they are JWTs signed with `JWT_SECRET`. A random value there
produces a stack that starts and then rejects every request.

`.env.example` lists every variable this compose file interpolates, and ends
with a block naming the upstream variables that are deliberately absent
(`VAULT_ENC_KEY`, `POOLER_*`, `LOGFLARE_*`, `DASHBOARD_*`, `PG_META_CRYPTO_KEY`
and friends) so nobody re-adds them by pattern-matching against upstream.

## Upgrading to a newer upstream tag

The point of vendoring is that an upgrade is a diff you can read.

```bash
# 1. Fetch the candidate tag into a scratch directory (NOT inside this repo).
cd /tmp && rm -rf supabase-src
git clone --depth 1 --branch self-hosted/v0.7.x --filter=blob:none --sparse \
  https://github.com/supabase/supabase.git supabase-src
cd supabase-src && git sparse-checkout set docker

# 2. Diff upstream-vs-upstream first: what actually changed between the tag
#    recorded above and the new one? That is the change you are adopting.
git log --oneline 244301c09ddba21aa963ebea09e712ce89b0401a..HEAD -- docker/
cat docker/versions.md   # image bumps, newest first

# 3. Then diff each vendored file against its new upstream counterpart and
#    replay only the changes that touch a service we keep.
diff -u /tmp/supabase-src/docker/docker-compose.yml ops/supabase/docker-compose.yml
diff -u /tmp/supabase-src/docker/volumes/api/kong.yml ops/supabase/volumes/api/kong.yml
for f in realtime.sql roles.sql jwt.sql webhooks.sql; do
  diff -u "/tmp/supabase-src/docker/volumes/db/$f" "ops/supabase/volumes/db/$f"
done
```

After replaying, re-run the checklist that made this stack safe:

- every `image:` pinned to an exact tag, no `latest`;
- **no `depends_on` names a service we do not run** — the fastest check is
  `docker compose config --services` plus reading each `depends_on`;
- Kong still `127.0.0.1:8000`, `db` still publishes nothing;
- `restart: unless-stopped` and `mem_limit` still on all six;
- `wal_level=logical` and `max_slot_wal_keep_size=512MB` still in the db command;
- `docker compose --env-file <copy of .env.example> config --services | sort`
  prints exactly `auth db kong realtime rest storage`.

Then take a backup, `systemctl stop supabase`, `docker compose pull`,
`systemctl start supabase`, and watch `docker compose logs -f auth storage` for
migration errors — GoTrue and Storage run their own schema migrations on boot.

Also update the provenance table at the top of this file, and the header
comment of `docker-compose.yml`. A vendored file whose recorded tag is wrong is
worse than one that is merely old.

**Two upgrade constraints carried from the plan:** the self-hosted GoTrue image
must be at least as new as the cloud project's, or restored `auth` rows will
reference columns it does not have; and never cross to `self-hosted/v0.8.0+`
without re-verifying the whole Kong/nginx path.
